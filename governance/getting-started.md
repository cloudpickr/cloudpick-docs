# 클라우드 거버넌스 시작하기

> 문서 기준: 2026년 5월

## 왜 거버넌스인가

온프레미스에서는 서버를 구매하려면 품의서를 올리고, 승인을 받고, 발주하고, 설치해야 합니다. 이 절차 자체가 통제 역할을 했습니다. 아무나 서버를 만들 수 없었으니까요.

클라우드에서는 API 한 번이면 리소스가 생깁니다. 이 속도가 장점이지만, 통제 없이 사용하면 비용 폭증, 보안 사각지대, 규제 위반이 빠르게 누적됩니다. **거버넌스는 이 속도를 유지하면서도 조직이 통제력을 잃지 않게 하는 구조**입니다.

{% hint style="warning" %}
거버넌스는 "느리게 만드는 것"이 아닙니다. 잘 설계된 거버넌스는 가드레일 안에서 팀이 자율적으로 빠르게 움직일 수 있게 합니다. 거버넌스 없이 빠르게 가면, 나중에 더 느려집니다.
{% endhint %}

## 핵심 영역

| 영역 | 질문 | 없으면 생기는 일 |
| --- | --- | --- |
| **계정/조직 구조** | 누가 무엇을 만들 수 있는가? | 리소스 난립, 비용 추적 불가, 보안 경계 모호 |
| **[비용 관리 (FinOps)](finops.md)** | 얼마나 쓰고 있고, 적정한가? | 예산 초과, 좀비 리소스, 약정 낭비 |
| **[규정 준수](compliance.md)** | 우리 산업의 규제를 충족하는가? | 감사 지적, 인증 실패, 서비스 중단 명령 |
| **[재해복구 (DR)](dr.md)** | 장애 시 얼마나 빨리 복구하는가? | 리전 장애 시 서비스 장기 중단 |
| **[벤더 종속성과 출구 전략](exit-strategy.md)** | 벤더를 바꿔야 할 때 나갈 수 있는가? | 협상력 상실, 가격 인상에 무방비 |

## 어디서부터 시작하는가

거버넌스를 한 번에 완벽하게 구축하려 하면 도입이 지연됩니다. 다음 순서로 점진적으로 확장하는 것이 현실적입니다.

1. **계정 구조와 [랜딩존](landing-zone.md)** — 조직 구조, 환경 분리, 기본 가드레일부터
2. **비용 가시성** — 누가 얼마 쓰는지 보이게 만들기 (태그 정책, 대시보드)
3. **규정 준수 기반** — 산업별 필수 인증 확인, 감사 로그 중앙화
4. **DR 전략** — 워크로드별 RPO/RTO 정의, 최소한의 복구 계획
5. **출구 전략** — 종속성 인벤토리, 이식성 확보 방안
